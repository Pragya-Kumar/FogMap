
# FogMap — AI-Based Fog Monitoring and Alert System

## 1. Project Overview

FogMap is an AI-based fog monitoring and alert system designed to assist highway traffic management authorities in identifying reduced-visibility conditions from camera images.

The system uses a deep-learning image classification model to classify road-scene images into:

- **Clear**
- **Smog/Fog**

The prediction generated by the AI model is processed through a FastAPI backend and stored in a PostgreSQL database hosted on Neon. A Streamlit-based monitoring dashboard presents detection results, confidence scores, visibility levels, alerts, trends, geographical risk visualization, and recent detection logs.

The current implementation is a **software-only prototype**. The deployed system currently demonstrates the complete software pipeline using test/sample detections. Integration with live highway CCTV/IP-camera streams is planned as the next deployment stage.

---

# 2. Objectives

The main objectives of FogMap are:

1. Detect reduced-visibility conditions from road images using artificial intelligence.
2. Classify input images into Clear and Smog/Fog conditions.
3. Calculate the confidence of each prediction.
4. Convert model predictions into visibility and alert levels.
5. Store detection results in a centralized PostgreSQL database.
6. Provide a web-based monitoring dashboard for authorities.
7. Provide geographical visualization of detected risk locations.
8. Maintain detection logs for monitoring and analysis.
9. Provide a software architecture that can later accept live camera streams.
10. Deploy the backend, database, and dashboard using cloud services.

# 4. Major Components

## 4.1 AI Model

FogMap uses a TensorFlow/Keras image-classification model for detecting visibility conditions.

The model performs binary classification:


0 → Clear
1 → Smog


The model receives an image and produces a prediction confidence.

The inference pipeline resizes input images to:


224 × 224 pixels


The prediction threshold is used to determine whether the image is classified as Clear or Smog.

---

## 4.2 FastAPI Backend

The backend provides the API layer between the AI model, database, and external clients.

The backend is responsible for:

* Receiving image input.
* Preparing the image for inference.
* Loading the trained TensorFlow model.
* Performing prediction.
* Calculating confidence.
* Determining visibility level.
* Determining alert status.
* Recording prediction latency.
* Storing detection information in PostgreSQL.

The backend is deployed as a web service on Render.

---

## 4.3 PostgreSQL Database

FogMap uses PostgreSQL for persistent storage.

The production database is hosted using Neon.

The primary database entities are:

### `fog_detections`

Stores individual AI detection results.

Important fields include:

* Detection ID
* Timestamp
* Camera location
* Prediction label
* Confidence score
* Visibility level
* Alert status
* Processing latency

### `active_alerts`

Stores alerts generated from detection results.

Important fields include:

* Alert ID
* Detection ID
* Alert level
* Resolution status

---

## 4.4 Streamlit Dashboard

The Streamlit application provides the monitoring interface.

The dashboard provides:

* Latest detection status
* Visibility status
* Total detections
* Active alerts
* Average inference latency
* Confidence trends
* Fog/Smog frequency analysis
* Visibility distribution
* Camera-location risk visualization
* Recent detection logs
* Alert resolution controls

The dashboard is intended to provide an operational view for highway traffic monitoring personnel.

# 10. Prediction and Alert Logic

The system converts the model prediction into an operational visibility level.

For Smog/Fog predictions, the visibility level is determined using the prediction confidence.

The system also determines whether an alert should be generated according to the configured confidence thresholds.

The resulting information is stored in the database and displayed on the dashboard.

This separation allows the machine-learning prediction layer and the operational alert layer to remain independently configurable.

# 20. Model Retraining for Live Cameras

Connecting a live camera does **not automatically require retraining the model**.

The existing model can initially be tested on frames from the live camera.

However, real highway camera footage may differ from the original training data because of:

* Camera position
* Weather conditions
* Lighting
* Night-time scenes
* Camera resolution
* Compression
* Road environment
* Regional conditions

Therefore, a future production deployment should collect representative highway-camera images and evaluate model performance.

If performance is insufficient, the collected data can be labeled and used for:


Data Collection
      ↓
Data Labelling
      ↓
Dataset Expansion
      ↓
Fine-Tuning / Retraining
      ↓
Model Evaluation
      ↓
Deployment

# 22. Known Limitations

The current prototype has the following limitations:

1. Live highway CCTV/IP-camera integration is not currently implemented.
2. Current dashboard records include sample/test detections for demonstration.
3. Model performance may vary on camera footage that differs from the training dataset.
4. Production-scale multi-camera processing requires additional infrastructure.
5. Continuous video processing requires appropriate compute and bandwidth resources.
6. The current deployment is intended as a software prototype rather than a certified highway safety system.

These limitations are intentionally documented so that future developers do not interpret the prototype as an already deployed national highway monitoring system.
